### 0.3 当前主要缺口（本方案要解决的问题）

1. **任务恢复只覆盖补贴采集**：`page.taskKey = "vietnam_subsidy_collection"` 单值。用户在马帮导出、退款合并或最终生成运行中刷新页面，进度和日志全部丢失，且可能误以为任务没在跑而重复点击。
2. **页面不会引导用户**：三个 Tab 永远默认停在“报表概览”；没有“当前应该做哪一步”的推导；按钮禁用时不显示原因。
3. **中断状态无法识别**：应用重启后若 manifest 里残留 `running`，页面会一直显示“运行中”，用户无法判断是否该重试。
4. **店铺汇总表功能单薄**：无搜索、无排序、无总计行、异常行不置顶；列较少（缺订单数、综合支出、实际退款）。
5. **结果文件入口分散**：报表生成后没有一个固定区域展示 Excel / 未匹配 CSV / 处理日志 / 输出目录四个入口；文件被移动后页面无提示。

## 1. 设计原则

本方案的每一条改动都必须满足：

1. **不改业务口径**：不动采集流程、校验公式、利润计算，只做展示层和状态层。
2. **小步可回退**：按 R1→R4 四个阶段实施，每个阶段独立可交付、可单独回退，改完即跑测试。
3. **向后兼容**：
   - 内部标识（页面 key、任务 tool key、API 名、manifest schema、历史目录 `越南收支核对`）一律不改；
   - 旧 manifest 缺少新字段时用默认值兜底，不报 KeyError；
   - 旧版 Bridge 缺少 API 时前端捕获异常并降级，页面不能白屏。
4. **公共代码零风险扩散**：改 `common.js` 时必须保持其他页面现有单 `taskKey` 行为完全不变，新能力只通过新增可选字段（`page.taskKeys`）启用。
5. **用户视角文案**：所有新增提示用业务语言（“马帮收支校验未通过，请重新导出”），技术细节只进日志。

## 2. R1：多任务恢复与中断识别（最高优先级）

**解决的问题**：缺口 1、缺口 3。这是稳定性收益最大的一步——它防止用户在任务运行中刷新后重复启动任务。

### 2.1 `common.js` 支持 `page.taskKeys`（向后兼容扩展）

在 `initialize(page)` 中现有逻辑：

```javascript
if (page.taskKey) await restoreLatestTask(page.taskKey);
```

扩展为：

```javascript
if (Array.isArray(page.taskKeys) && page.taskKeys.length) {
  await restoreLatestTaskFromKeys(page.taskKeys, page.taskContextFilter);
} else if (page.taskKey) {
  await restoreLatestTask(page.taskKey);
}
```

新增 `restoreLatestTaskFromKeys(tools, contextFilter)`：

1. 对每个 tool 调用 `api().get_latest_task_status(tool)`（已有 API，逐个调用并 catch，单个失败不影响其余）；
2. 过滤掉 `empty` 结果；若提供 `contextFilter`，只保留 `contextFilter(task.context)` 为真的任务（用于“只恢复当前批次的任务”）；
3. 优先选 `status` 为 `running/pending` 的任务；多个运行中任务取 `created_at` 最新（正常情况下互斥锁保证同批次最多一个）；
4. 没有运行中任务时，取 `created_at` 最新的已结束任务，仅回显其结果与日志，不启动轮询；
5. 选中后走现有 `renderTask + startPolling` 路径，不新建第二套轮询。

**约束**：`restoreLatestTask` 原函数一个字符都不改，其他页面行为不受影响。

### 2.2 越南页面接入五个任务 key

`frontend/assets/pages/vietnam-income-reconciliation.js`：

```javascript
const VIETNAM_TASK_KEYS = [
  "vietnam_subsidy_collection",
  "vietnam_ziniao_sources_collection",
  "vietnam_mabang_income_collection",
  "vietnam_mabang_refund_collection",
  "vietnam_final_reconciliation",
];

const page = {
  key: "vietnam_income_reconciliation",
  taskKeys: VIETNAM_TASK_KEYS,
  taskContextFilter: (context) =>
    !manifestPath || !context?.manifest_path || context.manifest_path === manifestPath,
  ...
};
```

保留 `taskKey: "vietnam_subsidy_collection"` 字段作为旧版 common.js 的兜底（新逻辑命中 `taskKeys` 后不会再读它）。

### 2.3 中断状态识别（“上次运行已中断”）

TaskManager 是内存任务管理器，应用重启后 task id 全部失效。在 `loadDashboard` 内，拿到 manifest 后做一次检测：

1. 收集 manifest 中所有 `status === "running"` 的报表项（紫鸟各店铺 reports、mabang reports、final）；
2. 若存在 running 项，但 `restoreLatestTaskFromKeys` 没有恢复到任何 live 的 `running/pending` 任务，则：
   - 对应步骤状态显示为「上次运行已中断，可重试」（橙色 `attention` 样式，不是红色失败）；
   - 页面顶部徽标不显示“运行中”，显示“需要处理”；
   - 相关“开始/重试”按钮保持可用。
3. **只改内存展示，不回写 manifest**——避免“打开页面”这个只读动作修改历史文件。

### 2.4 R1 验收标准

- 马帮收支导出运行中刷新页面：进度、日志、按钮禁用状态完整恢复；
- 最终生成运行中刷新页面：同上，完成后自动刷新 Dashboard 并弹出成功提示；
- 应用重启后打开页面：不显示任何“运行中”，残留 running 项显示“上次运行已中断，可重试”；
- 其他模块页面（shopee-ads、bigseller-sync 等）任务恢复行为与改动前完全一致；
- 新增 `tests/test_task_manager.py` 用例：context 过滤、多 tool 最新任务选择。

## 3. R2：状态推导与页面引导

**解决的问题**：缺口 2。让用户进入页面 5 秒内知道“现在处于什么状态、下一步点哪里”。

### 3.1 前端纯函数 `deriveVietnamReportState`

不依赖单一 `manifest.status`，综合 dashboard state、live task、文件存在性推导：

```javascript
function deriveVietnamReportState(dashboard, activeTask) {
  // 返回 { kind, label, activeTab, primaryActionId, primaryHint, blockers: [] }
}
```

推导优先级（从高到低）：

| 条件 | kind | 默认 Tab | 主操作提示 |
| --- | --- | --- | --- |
| 有 live running 任务 | `running` | 数据准备 | 查看处理进度（展开日志抽屉） |
| dashboard.state = `generating` | `generating` | 数据准备 | 等待生成完成 |
| dashboard.state = `blocked`（校验失败/采集失败） | `blocked` | 异常核对 | 按异常项的 action 重试 |
| dashboard.state = `needs_attention`（缺利润率） | `needs_attention` | 数据准备（步骤四） | 填写利润率 |
| dashboard.state = `ready_to_generate` | `ready_to_generate` | 数据准备（步骤四） | 生成收支报表 |
| dashboard.state = `ready` / `ready_with_issues` | 同名 | 报表概览 | 打开 Excel 报表 |
| dashboard.state = `final_file_missing` | `failed` 变体 | 报表概览 | 重新生成（显示“文件已不存在”持久提示） |
| 无批次 / draft | `empty` / `draft` | 数据准备（步骤一） | 创建报表批次 |

### 3.2 Tab 自动选择规则（防抢占）

- 仅在三种时机应用自动选择：页面初始化、用户切换批次、任务完成导致 state 跨档变化（如从 `ready_to_generate` 变为 `ready`）；
- 用户手动点过 Tab 后，普通轮询刷新一律不改变当前 Tab（用一个 `userPinnedTab` 标记实现）；
- 向导步骤同理：自动展开推导出的当前步骤，但用户手动点击步骤后不抢回。

### 3.3 禁用原因提示

为“开始导出收支并校验”“合并马帮退款”“生成核对工作簿”三个按钮增加下方提示行（`<small class="btn-hint">`）：

- 按钮可用时提示行为空；
- 按钮禁用时列出具体缺项，例如：
  - `还需完成：紫鸟广告消费（8/12 家）`
  - `已阻断：马帮收支校验未通过，请先到「异常核对」处理`
  - `还缺 2 家店铺利润率：店铺A、店铺B`
- 数据来源：dashboard 的 `data_progress`、`exceptions`、`required_profit_rate_stores` 与 `config.profit_rates` 差集，全部是已有字段，不需要新后端接口。

### 3.4 校验失败的专属表达

马帮校验失败时（`mabang.validation.status === "failed"`）：

1. 页面顶部显示持久红色横幅（`role="alert"`）：“马帮收支明细与汇总不一致，当前不能生成报表。请重新导出并校验。”
2. 步骤三状态框显示明细/汇总订单数、订单差异、应收差异（R0 已接入字段，这里补充 `store_mismatches` 店铺级差异表，渲染进异常 Tab）；
3. 步骤四整体加锁样式并显示锁定原因。

### 3.5 R2 验收标准

- 五种状态（无批次 / 采集中 / 校验失败 / 可生成 / 已生成）下打开页面，默认 Tab 与主操作提示均符合上表；
- 手动切 Tab 后触发一次轮询刷新，Tab 不跳动；
- 生成按钮禁用时始终能看到具体原因，不再出现“灰着但不知道为什么”的按钮；
- 校验失败场景可通过异常 Tab 的“重试”动作直接触发重新导出。

## 4. R3：报表概览增强

**解决的问题**：缺口 4、缺口 5。让“报表概览”成为真正可用的结果页。

### 4.1 店铺汇总表增强

当前列（店铺/应收/最终广告/联盟/利润/利润率/状态）基础上：

1. **补列**：订单数（`order_count`）、综合支出（`total_expense`）、实际退款（`actual_refund`）——字段已在 summary JSON `stores` 中；
2. **搜索框**：按店铺名称过滤（前端内存过滤即可，店铺数 ≤ 200）；
3. **状态筛选**：全部 / 正常 / 有异常 三档；
4. **排序**：应收、支出、利润、利润率四列点击表头数值排序（必须 `Number(value)` 排序，不能按格式化字符串排）；
5. **默认排序**：异常行置顶，其余按利润降序；
6. **总计行**：表格底部固定一行显示 `totals`（直接用 API 的 totals，不在前端重新求和，保证与 KPI 一致）；
7. **空筛选结果**：显示“未找到符合条件的店铺”和“清除筛选”按钮。

表格容器保持 `overflow-x: auto`，店铺列冻结（`position: sticky; left: 0`），窄窗口横向滚动而不是压缩金额。

### 4.2 结果文件卡片

“报表概览” Tab 内新增固定卡片（仅已生成时显示）：

| 展示 | 数据来源 |
| --- | --- |
| Excel 文件名、生成时间 | `files.output_file`、`generated_at` |
| 平均汇率、明细行数、退款行数、未匹配数 | summary JSON 已有字段 |
| 打开 Excel 报表 | `open_path(files.output_file)` |
| 打开未匹配清单 | `open_path(files.unmatched_file)`，无未匹配时按钮隐藏 |
| 打开处理日志 / 打开输出目录 | `files.processing_log` / `files.run_dir` |

**文件丢失处理**：dashboard 返回的 `files.output_file` 为空字符串但 manifest final.status 为 ready 时（即文件被移动/删除），卡片显示持久错误“报表文件已被移动或删除，请重新生成”，主操作改为“重新生成报表”，KPI 显示 `—` 而不是 0。

> 依赖后端小改动：`get_vietnam_report_dashboard` 增加 `output_exists`/`unmatched_exists` 布尔字段（`files` 内），旧前端忽略新字段无影响。

### 4.3 历史批次选项优化

`historyRunsList` 项显示格式统一为：

```text
2026-05-31 10:20 · 已生成 · 12 家店铺
```

即 `updated_at` + 状态标签 + `store_count`（字段均已返回）。切换批次时清空当前日志视图与任务状态，防止上一批次的日志残留（对应改造方案场景六）。

### 4.4 R3 验收标准

- 概览表格支持搜索、筛选、排序、总计行，金额按数值排序；
- 页面 KPI、总计行、Excel 汇总页三者数值一致；
- 已生成批次能一键打开 Excel / 未匹配 CSV / 日志 / 目录；
- 手动移走 Excel 后刷新：显示文件丢失提示，不显示 0 数据；
- 切换历史批次后无上一批次数据残留。

## 5. R4：健壮性收尾（可选，不阻塞 R1-R3 交付）
